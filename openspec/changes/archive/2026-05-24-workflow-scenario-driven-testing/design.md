## Context

現状の開発フローでは、テストケース設計（`general.md` Step 2）がユニットテストを主眼に置いており、E2Eテストは実装後に追加される傾向がある。また、Mock（localhost）と Preview（実API）の環境区別は実装コード（`isMockMode`）にしか現れず、設計段階での判断が記録されない。フロントエンド（Vitest / Playwright）とバックエンド（go test / testcontainers）のテスト戦略がそれぞれのルールファイルに分散しており、全体像を俯瞰する場所がない。

## Goals / Non-Goals

**Goals:**
- テスト戦略の全体像（6スコープ）を一箇所 (`testing.md`) で定義し、スコープ選択の判断基準を明文化する
- proposal.md にユーザーシナリオ + テスト設計（ハイブリッド形式）を標準セクションとして組み込む
- レビューで生まれた判断基準をドキュメントに蓄積できる構造を作る
- archive 時にユーザーシナリオを spec.md へ昇格させる手順を確立する

**Non-Goals:**
- 既存の E2E テストコードをリファクタリングすること
- テストフレームワーク・ツールを変更すること
- CI/CD パイプラインを変更すること

## Decisions

### D-1: testing.md の配置場所を `.claude/rules/` にする

**選択肢:**
- A) `.claude/rules/testing.md`（採用）
- B) `specs/testing-strategy/spec.md`
- C) `frontend.md` / `backend.md` に統合

**理由:** `.claude/rules/` は Claude が参照する開発ルールの置き場であり、判断基準の更新ログも含むため、コードと同じリポジトリで管理しつつ Claude に自動参照させるのに最適。`specs/` は機能仕様書の場所であり、ワークフロールールとは役割が異なる。

---

### D-2: テスト設計フォーマットはハイブリッド形式（サマリテーブル + G/W/T）

**選択肢:**
- A) テーブルのみ
- B) G/W/T のみ
- C) ハイブリッド（採用）

**理由:** サマリテーブルで全シナリオを俯瞰し、G/W/T で「ブラウザが必要か」「外部APIが必要か」を自然に問える。テーブルだけでは E2E 判定の根拠が書きにくく、G/W/T だけでは一覧性が低い。

---

### D-3: バックエンドシナリオも proposal.md に含める

**選択肢:**
- A) フロントエンドシナリオのみ（E2Eに絞る）
- B) フロントエンド + バックエンド両方（採用）

**理由:** 「どの検証観点をどのスコープで実現するか」を一箇所で判断できるようにするため。APIレイヤーの G/W/T（例: `POST /stock-items` が 201 を返す）も含めることで、Frontend Unit で mock すべき境界が明確になる。

---

### D-4: 判断基準の更新ログを testing.md 内に持つ

**構造:**
```
testing.md
├── テストスコープ定義
├── スコープ選択基準（判断ツリー）
├── テスト設計フォーマット
└── 判断基準の更新ログ（日付・理由・追加された基準）
```

レビューで「このシナリオは Integration で十分」と判断された理由を更新ログとして残す。Claude は次回の設計時にこのログを参照して判断基準を適用する。

## Risks / Trade-offs

- **proposal.md が長くなる** → シナリオが多い change では設計セクションが肥大化する可能性がある。シナリオが 6 件以上になる場合は別ファイルに切り出す指針を testing.md に記載する
- **判断基準の陳腐化** → testing.md の更新ログが形骸化するリスク。archive 手順の中に「判断基準を更新したか」のチェックポイントを明示することで対処
- **バックエンドシナリオの粒度** → APIレベルのシナリオ（HTTP リクエスト/レスポンス）はユーザー操作シナリオより粒度が細かいため、混在すると読みにくくなる。フロントエンド（ユーザー操作）とバックエンド（API契約）でセクションを分割する

# アクセストークン有効期限を 24 時間に延長する

- 日付: 2026-10-18
- Issue: #304
- 種別: 本番設定の変更（Supabase ダッシュボード、コード変更なし）

## 決定

Supabase Auth のアクセストークン有効期限（JWT expiry）を **3600 秒（1 時間）→ 86400 秒（24 時間）** に変更する。

## 背景（実測）

2026-10-18 に Supabase の edge logs と Vercel のランタイムログを突き合わせ、実ユーザーの `/stock-items` 初回表示 1 件を時系列で追った（Hobby プランのログ保持は 1 時間のため n=1）。

| 時刻 (UTC) | 出来事 |
|---|---|
| 07:35:59.629 | リクエスト到着 |
| 07:35:59.810 | middleware がトークンをリフレッシュ（`POST /auth/v1/token`、上流 443ms） |
| 07:36:00.126 | middleware が並列で投げた `fetchStockItems` が HTTP 401（期限切れトークンを使用） |
| 07:36:00.551 | page 側のフォールバック取得が完了（`fetchStockItems;dur=120.5`） |

サーバー側の所要時間 約 0.9 秒のうち、最大要因はトークンのリフレッシュだった。有効期限が 1 時間だと、1 時間以上あけて開くたびに次のことが起きる。

- リフレッシュ（約 400ms）が直列で入る
- `stock-items-ssr-prefetch` の並列プリフェッチ（PR #301）が期限切れトークンで空振りし、page 側の取り直しが直列で追加される

DB（アプリのクエリは平均約 0.12ms）はボトルネックではない。

家族共用アプリで 1 日に数回開く使い方を想定すると、24 時間ならその日の 2 回目以降はリフレッシュが不要になり、並列プリフェッチも効くようになる。

## 検討した選択肢

| 有効期限 | 評価 |
|---|---|
| 6 時間 | 間隔の短い再訪にしか効かず、効果が限定的 |
| 12 時間 | 朝・夜の利用はカバーできるが、翌朝の初回はリフレッシュが走る |
| **24 時間（採用）** | 1 日数回の利用ならほぼリフレッシュ不要。失効の反映は最大 1 日 |
| 1 週間（Supabase の上限） | ほぼ常にリフレッシュ不要だが、漏洩したトークンが最大 1 週間有効 |

## トレードオフと許容理由

サインアウトやアカウント削除をしても、発行済みのアクセストークンは期限まで（最大 24 時間）有効なまま残る。次の理由で許容する。

- 家族共用アプリで、扱うデータは在庫情報のみ
- Go API はリクエストごとに DB でグループ所属を確認している（`backend/middleware/auth.go`）。グループから外されたユーザーは、トークンが有効でもそのグループのデータにアクセスできない
- リフレッシュトークンの扱い（ローテーション等）は変わらない

## コードへの影響

1 時間を前提にしたコードはない。`frontend/src/lib/warmSession.ts` はセッションの `expires_at` を見て期限の 5 分前に取り直すため、そのまま動く。

## 効果確認の方法

変更後、1 時間以上（24 時間未満）あけてアプリを開いた直後に、次を確認する。

- Supabase edge logs: middleware（UA `Vercel Edge Functions`）からの `/auth/v1/token` が出ていない
- Vercel ランタイムログ: `middleware: fetchStockItems threw [Error: HTTP 401]` が出ていない
